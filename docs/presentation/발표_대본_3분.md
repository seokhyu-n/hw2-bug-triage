# 3분 발표 대본: 개발팀 업무 과제

연습용입니다. 본론은 1~10쪽이고, 11쪽부터는 부록이라 질문이 나왔을 때만 보여 줍니다.
화면을 보지 않고 들어도 무엇이 어떻게 됐는지 알 수 있게, 문장마다 이름과 값과 결론을 넣었습니다.
"이렇게", "이런 식으로", "이 부분은"이 입에서 나오면 그 자리에 숫자나 이름을 넣으세요.

**1쪽** 안녕하세요, 서석현입니다. 러닝 앱 RunBuddy에 들어오는 버그 제보를 AI가 분류하고, 정보를 뽑고, 점수를 매기고, 알려진 이슈와 이어 주는 서비스를 만들었습니다.

**2쪽** 과제 네 개 중 개발팀 업무를 골랐습니다. 제보를 읽고 나누고, 빠진 정보를 묻고, 급한 순서를 정하는 일에 사람 손이 많이 들기 때문입니다. 소재는 전공 수업에서 세 명이 함께 만든 RunBuddy입니다. 직접 만든 앱이라 실제로 나올 버그를 판단할 수 있었고, 예를 들어 거리가 짧게 기록되는 ISSUE-04는 앱 코드가 30m 넘게 튄 위치를 버리는 부분을 보고 만들었습니다.

**3쪽** 신고자가 글을 남기면 먼저 저장하고 접수 번호를 바로 줍니다. 그다음 Claude Haiku 5.5가 추출, 분류, 이슈 연결, 점수의 네 단계로 분석해서 담당 개발자에게 보냅니다.

**4쪽** 제보 한 건을 끝까지 보겠습니다. "10km를 뛰었는데 8.3km로 나왔다"는 제보입니다. AI는 안드로이드 12와 앱 1.1.0을 뽑고, 버그로 분류하고, 이슈 검색 도구를 불러 ISSUE-04를 골랐습니다. 유실은 아니지만 거리가 17% 짧아서 우선순위는 P2로 판단했습니다. 코드는 ISSUE-04가 도구가 실제로 돌려준 번호인지, 이미 고친 버전에서 난 재발이 아닌지 확인하고, 앱 버전·OS 버전·재현 순서가 다 있으니 완성도 2점을 계산합니다. 결과는 정답과 같았습니다.

**5쪽** 확인하는 코드는 두 줄이 핵심입니다. 도구가 돌려준 적 없는 번호면 연결하지 않고, 제보자가 이미 수정된 버전을 쓰면 재발로 보고 새 신고로 남깁니다.

**6쪽** 제가 내린 결정 네 가지입니다. AI가 없는 이슈 번호를 쓸 수 있어서 도구가 돌려준 번호만 연결했습니다. AI가 정보가 다 있는 제보에 1점을 줘서 완성도 1·2점은 코드가 계산하게 했습니다. 분석 중 오류가 나면 제보가 사라져서 먼저 저장하게 했고, 접수가 12초에서 0.02초가 됐습니다. Sonnet이 우선순위를 0.888로 더 잘 맞혔지만 비용이 약 18배라 Haiku를 유지했습니다.

**7쪽** 평가는 두 세트로 나눴습니다. 오류를 보며 고친 250건에서 완성도 오차가 0.120에서 0.043으로 줄었고, 우선순위는 0.864에서 0.871로 차이가 없었습니다. 세 번 모두 틀린 것이 분류 6건, 라벨 10건, 우선순위 22건 남았습니다. 튜닝에 쓰지 않은 100건에서는 완성도 오차가 0.147에서 0.018, 분류가 0.950에서 0.990이 됐습니다.

**8쪽** 효과가 컸던 수정 두 가지입니다. 완성도 계산을 코드로 옮겨 오차가 0.128에서 0.043이 됐습니다. 그리고 호출 방식을 바꾼 뒤 AI가 이슈 번호에 따옴표를 붙여 연결이 끊기던 오류를 고쳐, 이슈 연결이 0.948에서 0.993으로 돌아왔습니다. 이 오류는 250건을 재고서야 보였습니다.

**9쪽** 수정 1의 실제 사례입니다. 앱 버전, 안드로이드 버전, 재현 순서가 다 있는데 AI는 세 번 모두 1점을 줬습니다. 1점과 2점은 코드가 정하고 AI는 증상이 불명확한 0점만 정하게 바꾸자 세 번 모두 2점이 나왔습니다.

**10쪽** 한계입니다. 버그가 아닌 것을 버그로 본 것이 250건에서 회차마다 7, 5, 5건입니다. 버그를 놓치지 않으려고 버그 쪽으로 기울였기 때문이고, 버그를 놓친 것은 0, 0, 1건입니다. 정답은 AI가 썼고 사람이 본 것은 34건이라, 다음에는 실제 제보로 검증하겠습니다. 감사합니다.

## 부록 (질문이 나오면)

**12쪽** 완성도 정답도 같은 규칙인데 오차가 줄어든 것은 무엇을 뜻하나: AI가 규칙을 일관되게 지키지 못하던 문제를 코드가 없앴다는 뜻이고, AI 판단이 좋아졌다는 뜻은 아닙니다. 사람이 매긴 정답으로 다시 재야 확인됩니다.

**13쪽** 후보 중 잘못된 이슈를 AI가 고르면: 코드는 없는 번호, 재발, 아이폰을 막지만 증상이 다른 이슈나 영향 OS 범위 밖의 이슈는 못 막습니다. 지금은 규칙과 평가로 관리하고(250건 0.993, 새 100건 1.000), 개발자가 화면에서 연결을 바꿀 수 있습니다. 다음에는 영향 OS 범위도 코드로 확인하겠습니다.

**14쪽** 없는 기능을 버그로 보는 문제: 앱의 정상 동작 9가지를 분류 지시에 넣었고, 목록 밖은 고장 가능성이 있으면 버그로 봅니다. 규칙을 넓혔다가 진짜 버그 3건을 문의로 보낸 적이 있어서(V2-Run-09), 앱 기능 목록은 제품 담당자가 확정하고 새 사례로 다시 재야 합니다.

**15쪽** RunBuddy 앱 화면입니다. **16~17쪽** AI와 코드의 역할 표와 설계 원칙. **18쪽** 우선순위 P1~P4와 완성도 0~2점 기준. **19쪽** 고친 것 7가지 전체. **20쪽** 기법을 하나씩 끈 비교: 채점 기준표를 끄면 우선순위가 0.864에서 0.712로 가장 크게 떨어집니다. **21쪽** 공통 필수 조건 대응표. **22~30쪽** 신고자 화면과 개발자 화면.
