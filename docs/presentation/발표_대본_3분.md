# 3분 발표 대본: 개발팀 업무 과제

`→` 는 화면을 가리키라는 뜻입니다. 8~14쪽(화면, 점수 기준)과 16·17쪽(개선 사항, 기법 비교 표)은 **말하지 않고 빠르게 넘깁니다**(질문이 나오면 보여 주기). 20쪽은 부록(필수 조건 표)입니다.

## 1~2쪽. 과제와 이유 (20초)

안녕하세요, 서석현입니다. 개발팀 업무 과제로, 버그 제보를 AI가 정리해 주는 서비스를 만들었습니다.
소재는 팀으로 직접 만든 러닝 앱 RunBuddy입니다. 아는 앱이라 실제로 나올 법한 버그로 평가할 수 있었습니다.

## 3쪽. 구조 (20초)

→ 신고자가 글을 남기면 먼저 저장하고, AI가 네 단계로 분석합니다. 정보를 뽑고, 분류하고, 이미 아는 이슈를 찾고, 점수를 매겨 담당 개발자에게 보냅니다.

## 4~5쪽. 역할과 설계 (25초)

글을 이해하고 판단하는 일은 LLM이, 규칙이 정해진 일과 확인은 코드가 맡습니다.
핵심 설계는 **AI가 고르고 코드가 확인한다**입니다. AI는 없는 이슈 번호를 지어낼 수 있고 점수도 흔들리기 때문입니다.

## 6~7쪽. 핵심 로직: 이슈 조회 (35초)

→ “10km를 뛰었는데 8.3km로 나온다”는 실제 평가 사례입니다.
AI는 안드로이드 12와 앱 1.1.0을 뽑고 버그로 분류한 뒤, 외워서 답하지 않고 검색 도구로 이슈를 찾았습니다.
결과는 ISSUE-04이고 정답과 같았습니다.
→ 코드는 도구가 돌려준 번호인지 확인하고, 아니면 연결하지 않습니다.

## 15쪽. 결과 (35초)

→ 250건을 세 번씩 돌린 평균입니다. 완성도 오차가 0.120에서 0.043으로, 여러 라벨은 0.867에서 0.935로 좋아졌습니다. 우선순위는 거의 그대로입니다.
다만 250건은 오류를 보며 고친 세트라 실제보다 높을 수 있고, 전은 API, 지금은 헤드리스로 재서 조건이 다릅니다.

## 18쪽. 틀린 사례 (25초)

→ 버전과 재현 순서가 다 있는 제보인데, AI가 완성도를 세 번 모두 1점으로 줬습니다.
규칙으로 셀 수 있는 일을 AI에게 맡긴 것이 원인이었습니다. 코드가 정하게 바꾸자 세 번 모두 정답인 2점이 나왔습니다.

## 19쪽. 한계 (20초)

정답을 AI가 썼고, 사람이 확인한 것은 34건입니다. 실제 사용자 제보로는 아직 검증하지 못했습니다.
다음은 실제 제보로 검증하고 속도를 높이는 것입니다. 감사합니다.
