# 발표 대본: 개발팀 업무 과제

전체 약 10~11분(천천히 읽었을 때 어림). 시간이 짧으면 **[줄여도 됨]** 쪽은 한 문장만 말하고 넘기세요.
`→` 표시는 화면을 가리키라는 뜻입니다.

---

## 1쪽. 표지 (20초)

안녕하세요. 개발팀 업무 과제를 발표할 서석현입니다.
저는 러닝 앱 RunBuddy에 들어오는 버그 제보를 AI가 읽고 정리해서, 담당 개발자에게 넘겨 주는 서비스를 만들었습니다.

## 2쪽. 선택 과제와 이유 (40초)

제가 고른 과제는 개발팀 업무입니다.
개발팀에는 제보가 계속 들어옵니다. 이게 버그인지 단순 문의인지 나누고, 빠진 정보를 다시 묻고, 뭐부터 고칠지 정하고, 이미 아는 문제인지 찾아봐야 합니다.

소재를 RunBuddy로 정한 이유는, 팀으로 직접 만들어 본 안드로이드 러닝 앱이기 때문입니다. 앱을 아는 만큼 실제로 나올 법한 버그로 평가해 볼 수 있었습니다.

## 3쪽. 제보 한 건이 지나가는 길 (50초)

→ 왼쪽부터 보시면, 신고자가 로그인 없이 문제를 적습니다.
서비스는 먼저 저장하고 접수 번호를 바로 줍니다. 분석이 느리거나 실패해도 제보가 사라지지 않게 하려는 것입니다.

→ 그다음 AI가 네 단계로 분석합니다.
첫째, 글에서 기기와 버전, 증상을 뽑습니다. 둘째, 버그인지 문의인지 나눕니다. 셋째, 버그라면 이미 아는 이슈인지 찾습니다. 넷째, 점수를 매깁니다.
앞 단계의 결과가 다음 단계의 입력이 되고, 결과는 담당 개발자 화면으로 갑니다.

## 4쪽. LLM과 코드가 맡은 부분 (40초)

역할을 이렇게 나눴습니다.
글을 이해하고 판단하는 일은 LLM이, 규칙이 정해진 일과 확인은 코드가 맡습니다.
→ 예를 들어 이슈 연결에서는 AI가 검색어를 정하고 이슈를 고르지만, 그 번호가 진짜 검색 결과에 있었는지는 코드가 확인합니다.

## 5쪽. 주요 설계: AI가 고르고 코드가 확인한다 (40초)

가장 중요하게 생각한 설계입니다.
AI는 없는 이슈 번호를 그럴듯하게 지어낼 수 있고, 같은 글에도 점수가 흔들립니다.
그래서 이슈 번호는 도구가 돌려준 것만 인정하고, 정보가 다 있는지는 코드가 셉니다.
규칙으로 답이 정해지는 일은 AI에게 맡기지 않는다는 원칙입니다.

## 6쪽. 실제 제보 한 건의 흐름 (50초)

핵심 로직으로 이슈 조회를 골랐습니다. 실제 평가 사례 한 건을 보겠습니다.

→ “한강에서 10km를 뛰었는데 기록에는 8.3km로 나온다”는 제보입니다.
AI는 여기서 안드로이드 12, 앱 1.1.0을 뽑고, 버그로 분류했습니다.
그리고 이슈를 외워서 답하지 않고 **이슈 검색 도구**를 불러 찾았습니다. 도구는 AI가 필요할 때 부르는 검색 기능이라고 생각하시면 됩니다.

→ 결과는 ISSUE-04, 거리가 실제보다 짧게 기록되는 문제입니다. 우선순위 P2, 완성도 2점으로 정답과 같았습니다.

## 7쪽. 핵심 코드 (40초) [줄여도 됨]

→ 확인하는 코드입니다.
`seen`은 도구가 실제로 돌려준 번호 목록입니다. AI가 고른 번호가 여기에 없으면 연결하지 않습니다.
→ 아래쪽은 재발 확인입니다. 제보자가 이미 수정된 버전을 쓰고 있는데 같은 증상이 났다면, 다시 생긴 문제일 수 있으니 새 신고로 남깁니다.

## 8쪽. 신고자 화면 (30초)

실제 화면입니다.
→ 신고자가 글을 적고 신고하기를 누르면, → 알려진 문제와 점검 방법을 먼저 보여 줍니다. 해결되면 신고하지 않아도 되고, 그래도 신고할 수 있습니다.

## 9쪽. 개발자 화면 (40초)

→ 같은 제보가 개발자 화면에 나온 모습입니다. P2, 완성도 2점 만점에 2점, ISSUE-04로 정리됐습니다.
→ 오른쪽은 챗봇입니다. “P1만 보여줘”라고 하면 도구로 조회해서 답하고, 어떤 도구를 썼는지도 보여 줍니다.
이 화면은 임시 데이터로 실제 앱을 실행해서 찍은 것입니다.

## 10쪽. 우선순위와 완성도 (40초)

결과를 보기 전에 점수 두 가지를 설명드리겠습니다.
우선순위는 **얼마나 급한지**, 완성도는 **정보가 얼마나 충분한지**입니다.
예를 들어 “자꾸 튕겨요”는 앱이 꺼지니 급해서 P1이지만, 버전도 방법도 없어서 완성도는 1점입니다. 급한 것과 정보가 충분한 것은 별개입니다.

## 11쪽. 결과 요약 (70초)

→ 태스크별 평가 결과입니다. 왼쪽은 250건, 오른쪽은 새로 만든 100건이고, 각각 세 번씩 돌린 평균입니다.

가장 많이 좋아진 것은 완성도입니다. 정답과의 평균 차이가 250건에서 0.120에서 0.043으로 줄었습니다.
여러 라벨은 0.867에서 0.935로, 지어낸 값의 비율은 0.038에서 0.022로 좋아졌습니다.
반면 우선순위는 0.864에서 0.871로 거의 그대로입니다.

숫자를 볼 때 주의하실 점이 있습니다.
250건은 오류를 보면서 고친 세트라서 실제보다 높을 수 있습니다. 완성도는 정답도 같은 기준으로 만들어서 좋게 나오는 면이 있습니다. 그리고 예전 값은 API로, 지금 값은 Claude Code 헤드리스로 재서 조건이 다릅니다.

## 12쪽. 개선 사항 표 (60초)

→ 고친 것을 정리한 표입니다. 앞은 문제, 가운데는 고친 방법, 오른쪽은 전과 후입니다.
두 가지만 말씀드리겠습니다.
3번, AI가 완성도를 잘못 세어서 코드가 계산하게 바꿨고 오차가 0.128에서 0.043으로 줄었습니다.
5번, 이슈 번호에 따옴표가 붙어 나와 연결이 끊겼던 오류입니다. 측정하지 않았으면 놓쳤을 문제입니다.
1번과 5번의 전 값, 4번은 한 번만 잰 값이라 작은 차이는 조심해서 봐야 합니다.

## 13쪽. 기법 비교 (50초) [줄여도 됨]

→ 기법을 하나씩 꺼서 효과를 쟀습니다.
채점 기준표를 끄면 우선순위가 0.864에서 0.712로, 완성도 오차는 0.120에서 0.403으로 나빠집니다. 효과가 가장 큽니다.
반면 4단계로 나누는 것은 모든 면에서 좋지는 않았습니다. 완성도는 한 번에 시킨 쪽이 더 좋았습니다.

## 14쪽. 틀린 사례 1건 (50초)

틀렸던 사례입니다.
→ “저장에 실패했습니다”라는 제보인데, 앱 버전과 안드로이드 버전, 재현 순서가 다 있었습니다. 그러면 완성도는 2점이어야 하는데 AI는 세 번 모두 1점을 줬습니다.

→ 원인은 규칙으로 셀 수 있는 것을 AI에게 맡긴 것이었습니다.
그래서 1점과 2점은 코드가 정하게 바꿨고, → 세 번 모두 2점이 나왔습니다.
다만 이 사례를 보고 만든 수정이라는 점은 말씀드려야 할 것 같습니다.

## 15쪽. 한계와 다음 단계 (60초)

마지막으로 한계입니다.
250건 중 세 번 모두 틀린 것이 분류 6건, 라벨 10건, 우선순위 22건 남아 있습니다.
예를 들어 “자동 일시정지가 안 돼요”는 원래 없는 기능인데, AI는 버그로 봅니다. 제품을 모르면 알 수 없는 것이라 사람의 확인이 필요합니다.

데이터에도 한계가 있습니다. 사례와 정답을 AI가 썼고, 사람이 하나씩 확인한 것은 판단이 갈리는 34건입니다. 실제 사용자 제보로는 아직 검증하지 못했습니다.

다음 단계는 실제 제보로 검증하고, 정답을 사람이 더 검토하고, 분석 속도를 높이는 것입니다.

이상으로 발표를 마치겠습니다. 감사합니다.

## 16쪽. 부록: 필수 조건 (질문이 나오면 보여 주기)

→ 공통 필수 조건을 서비스에 어떻게 넣었는지 정리한 표입니다.
한 건 분석 시간은 Haiku API가 8.9초, 지금 쓰는 헤드리스가 21.9초로 더 느립니다. API 키가 필요 없는 대신 시간이 늘었습니다.

## 막힐 때 쓰는 한 문장

- **도구가 뭐냐고 하면:** AI가 외워서 답하지 않고, 필요할 때 부르는 검색 기능입니다.
- **MAE가 뭐냐고 하면:** 정답과 평균 몇 점 차이 나는지입니다. 작을수록 좋습니다.
- **헤드리스가 뭐냐고 하면:** Claude Code를 화면 없이 프로그램에서 부르는 방식입니다. API 키 대신 로그인 계정을 씁니다.
- **왜 느리냐고 하면:** 호출할 때마다 Claude Code를 새로 켜서 한 건에 12~30초 걸립니다.
- **모르는 질문이면:** 그 부분은 아직 확인하지 못했습니다. 확인해서 말씀드리겠습니다.
