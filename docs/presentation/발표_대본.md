# 발표 대본: 개발팀 업무 과제

짧은 글은 `발표_대본_3분.md`에 있습니다. 이 파일은 더 길게 설명할 때 씁니다.
본론은 1~10쪽, 약 7~8분(천천히 읽었을 때 어림)입니다. 시간이 짧으면 **[줄여도 됨]** 쪽은 첫 문장만 말하고 넘기세요.

11-25 발표 피드백을 반영한 규칙:
- 결과는 "평가 건수 → 전 → 후 → 아직 틀리는 것" 순서로, 숫자로 말합니다.
- 결정은 "문제 → 선택 → 이유" 순서로 말합니다. "AI가 추천해서"는 이유가 아닙니다.
- "이렇게", "이 부분은" 대신 이름과 값을 말합니다. 화면을 안 봐도 이해되는 문장이어야 합니다.
- 확인한 것은 단정해서 말하고, 모르는 것은 "확인하지 않았고, 확인하려면 ○○를 하면 됩니다"로 말합니다. "~인 것 같다"를 쓰지 않습니다.

## 1쪽. 표지 (15초)

안녕하세요. 개발팀 업무 과제를 발표할 서석현입니다.
러닝 앱 RunBuddy에 들어오는 버그 제보를 AI가 분류하고, 필요한 정보를 뽑고, 점수를 매기고, 알려진 이슈와 이어 주는 서비스를 만들었습니다.

## 2쪽. 선택한 과제와 이유: 문제 → 선택 → 이유 (40초)

**문제.** 개발팀에는 제보가 계속 들어옵니다. 버그인지 문의인지 나누고, 빠진 정보를 다시 묻고, 뭐부터 고칠지 정하고, 이미 아는 문제인지 찾는 데 사람 손이 많이 듭니다.
**선택.** 그래서 과제 네 개 중 개발팀 업무를 골랐고, 소재는 전공 수업에서 세 명이 함께 만든 안드로이드 러닝 앱 RunBuddy로 정했습니다.
**이유.** 직접 만든 앱이라 어떤 버그가 실제로 나올지 판단할 수 있습니다. 예를 들어 알려진 이슈 ISSUE-04, 거리가 실제보다 짧게 기록되는 문제는 앱 코드가 30m 넘게 튄 위치를 버리는 부분(RunningRepository.kt 139행)을 보고 만들었습니다.

## 3쪽. 제보 한 건이 지나가는 길 (40초)

신고자는 로그인 없이 문제를 적습니다. 서비스는 먼저 저장하고 접수 번호를 바로 줍니다.
그다음 Claude Haiku 5.5가 네 단계로 분석합니다. 첫째 추출은 기기·버전·증상을 뽑고, 둘째 분류는 버그·문의·개선 요청을 나누고, 셋째 연결은 도구로 알려진 이슈를 조회하고, 넷째 점수는 완성도와 우선순위를 매깁니다.
앞 단계의 결과가 다음 단계의 입력이 되고, 결과는 기능 영역에 맞는 담당 개발자 화면으로 갑니다.

## 4쪽. 제보 한 건을 끝까지 (70초)

평가 사례 E-010 한 건이 입력부터 결과까지 가는 과정입니다.

**입력**은 "갤럭시 A52s, 안드로이드 12, 앱 1.1.0. 한강에서 10km 뛰었는데 기록엔 8.3km로 나와요. 다리 밑을 지나갈 때부터 거리가 안 올라갔다"는 글입니다.

**LLM의 판단**은 네 가지입니다.
추출에서 안드로이드 12, 앱 1.1.0, 기능 영역은 기록 추적을 뽑았습니다.
분류는 버그입니다. 이유로 "이미 있는 거리 기록 기능의 오동작"을 적었습니다.
연결에서는 이슈를 외워서 답하지 않고 이슈 검색 도구를 불렀고, 돌아온 후보 중 "GPS 끊김 이후 거리가 누락된다"는 ISSUE-04를 골랐습니다.
우선순위는 P2입니다. 크래시나 기록 유실은 아니지만 핵심 기능인 거리가 17% 짧다는 근거를 먼저 쓰고 판단했습니다.

**코드의 확인과 계산**도 네 가지입니다.
ISSUE-04가 도구가 실제로 돌려준 번호인지 확인했고, 맞았습니다.
이미 고친 버전에서 난 재발인지 확인했고, ISSUE-04는 아직 수정 버전이 없어서 재발이 아닙니다.
완성도는 앱 버전·OS 버전·재현 순서가 모두 있으니 2점입니다. 이것은 AI가 아니라 코드가 셉니다.
기능 영역이 기록 추적이라 dev1에게 배정합니다.

**결과**는 ISSUE-04, 우선순위 P2, 완성도 2점이고, 빠진 정보가 없어서 제보자에게 질문하지 않습니다. 정답과 같습니다.

## 5쪽. 핵심 코드 (30초) [줄여도 됨]

확인 코드의 핵심은 두 줄입니다.
`seen`은 도구가 실제로 돌려준 번호 목록입니다. AI가 고른 번호가 여기에 없으면 연결하지 않습니다.
그리고 제보자가 이미 수정된 버전을 쓰는데 같은 증상이 났다면 재발이거나 다른 원인이라 새 신고로 남깁니다. 아이폰 제보는 안드로이드 전용 이슈에 연결하지 않습니다.

## 6쪽. 내가 내린 결정 (70초)

결정 네 가지를 문제, 선택, 이유 순서로 말씀드리겠습니다.

첫째, AI가 도구에 없는 이슈 번호를 그럴듯하게 쓸 수 있습니다. 그래서 도구가 돌려준 번호만 연결하게 했습니다. 틀린 연결은 새 버그를 "이미 아는 문제"로 닫아 버리기 때문입니다.

둘째, 정보가 다 있는 제보에 AI가 세 번 모두 완성도 1점을 줬습니다. 세 정보가 있는지는 규칙으로 정해지는 일이라 1점과 2점은 코드가 계산하게 했고, 250건 완성도 오차가 0.128에서 0.043으로 줄었습니다.

셋째, 처음에는 분석이 끝나야 저장해서, 오류가 나면 제보가 사라지고 신고자는 약 12초를 기다렸습니다. 먼저 저장하고 분석은 뒤에서 하게 바꿔 접수 응답이 약 0.02초가 됐고, 실패한 제보도 남아서 다시 분석할 수 있습니다.

넷째, 모델입니다. Sonnet 5.5가 250건 우선순위를 0.888로, Haiku의 0.864보다 잘 맞혔습니다. 하지만 비용이 약 18배이고 제보마다 네 번 호출하니, 남은 차이가 그 비용만큼은 아니라고 판단해 Haiku를 유지했습니다. Sonnet은 한 번만 쟀다는 점도 말씀드립니다.

## 7쪽. 결과 (70초)

평가는 두 세트로 나눴습니다. 개선에 쓴 세트와 확인용 세트입니다. 모두 세 번씩 돌린 평균입니다.

**개선에 쓴 250건**은 오류를 보며 고친 세트입니다.
완성도 오차는 0.120에서 0.043으로 줄었습니다.
여러 라벨 정확도는 0.867에서 0.935로 올랐습니다.
우선순위 일치는 0.864에서 0.871로, 차이를 확인하지 못했습니다.
세 번 모두 틀린 것이 분류 6건, 라벨 10건, 우선순위 22건 남아 있습니다.

**확인용 새 100건**은 튜닝에 쓰지 않은 세트입니다.
완성도 오차는 0.147에서 0.018, 분류는 0.950에서 0.990, 우선순위는 0.947에서 0.977이 됐습니다.
다만 이 세트도 결과를 한 번 본 뒤에 다시 잰 값이라 완전히 새것은 아닙니다.

조건도 말씀드립니다. 전은 튜닝 전 프롬프트를 API로, 후는 지금 설정을 Claude Code 헤드리스로 쟀습니다. 완성도는 정답도 코드와 같은 규칙으로 만들어서 좋게 나오는 면이 있습니다.

## 8쪽. 효과가 컸던 수정 2가지 (50초)

**수정 1.** 정보가 다 있는 제보에 AI가 1점을 주던 문제를, 1점과 2점은 코드가 정하게 바꿔 고쳤습니다. 250건 완성도 오차가 0.128에서 0.043이 됐습니다. 다음 쪽이 그 사례입니다.

**수정 2.** 호출 방식을 API에서 헤드리스로 바꾼 뒤 AI가 이슈 번호를 "ISSUE-04"처럼 따옴표까지 붙여 돌려줬고, 코드는 그것을 없는 번호로 보고 연결을 끊었습니다. 따옴표를 풀고 비교하게 고쳐 이슈 연결이 0.948에서 0.993으로 돌아왔고, 끊긴 12건이 모두 복구됐습니다. 몇 건만 돌려 봐서는 보이지 않았고 250건 평가에서 드러난 오류입니다.

나머지 다섯 가지는 부록 19쪽에 있습니다.

## 9쪽. 틀린 사례 1건 (40초)

"러닝 끝내기를 누르면 저장에 실패했다고 뜨고 기록이 저장되지 않는다, 1.1.1, 안드로이드 11"이라는 제보입니다.
앱 버전, 안드로이드 버전, 재현 순서가 다 있으니 완성도는 2점이어야 하는데, AI는 세 번 모두 1점을 줬습니다.
원인은 규칙으로 셀 수 있는 것을 AI에게 맡긴 것입니다. 1점과 2점은 코드가 정하고 AI는 증상이 불명확한 0점만 정하게 바꾸자 세 번 모두 2점이 나왔습니다.
이 수정은 이 사례를 보고 만들었습니다. 그래서 확인용 100건에서도 함께 쟀습니다.

## 10쪽. 한계와 다음 단계 (50초)

남은 한계는 세 가지입니다.

첫째, 버그가 아닌 것을 버그로 본 것이 250건에서 회차마다 7, 5, 5건입니다. 예를 들어 원래 없는 기능인 "자동 일시정지가 안 돼요"를 버그로 봅니다. 버그를 놓치는 쪽이 더 위험하다고 보고 버그 쪽으로 기울였고, 그 대신 버그를 놓친 것은 0, 0, 1건입니다.
둘째, 제품 정책을 알아야 하는 판단과 P1·P2의 경계는 사람이 확인해야 합니다.
셋째, 사례와 정답을 AI가 썼고 사람이 확인한 것은 판단이 갈리는 34건입니다. 실제 사용자 제보로는 검증하지 않았습니다.

다음 단계는 실제 제보로 검증하고, 정답을 사람이 더 검토하고, 이슈의 영향 OS 범위도 코드로 확인하고, 한 건에 12~30초 걸리는 분석 속도를 줄이는 것입니다.

이상으로 발표를 마치겠습니다. 감사합니다.

## 여기부터 부록 (질문이 나오면 보여 줌)

## 12쪽. 예상 질문 1: 완성도 정답도 같은 규칙이면 개선 수치는 무엇을 뜻하나

AI가 규칙을 일관되게 지키지 못하던 문제를 코드가 없앴다는 뜻입니다. E-131처럼 정보가 다 있는데 1점을 주던 경우가 사라졌습니다.
AI의 판단이 좋아졌다는 뜻은 아닙니다. 0점은 여전히 AI가 정하고, 추출이 틀리면 완성도도 함께 틀립니다.
확인하려면 사람이 매긴 완성도 정답으로 다시 재야 합니다. 지금 사람이 검토한 정답은 34건입니다.

## 13쪽. 예상 질문 2: 도구가 돌려준 후보 중 잘못된 이슈를 AI가 고르면

코드가 막는 것은 세 가지입니다. 도구 결과에 없던 번호, 이미 고친 버전에서 난 재발, 아이폰 제보와 안드로이드 전용 이슈의 연결입니다.
코드가 못 막는 것도 있습니다. 도구는 키워드가 맞는 이슈를 최대 5건 돌려주고 OS와 버전으로는 순서만 바꿉니다. 그래서 후보 안에서 증상이 다른 이슈나 영향 OS 범위 밖의 이슈를 고르는 것은 AI 판단에 맡겨져 있습니다.
지금은 "증상이 다르면 연결하지 않는다"는 규칙과 평가로 관리합니다. 이슈 연결 정확도는 250건 0.993, 새 100건 1.000이고, 반대 증상(E-004)과 OS 범위 밖(E-009) 같은 함정 사례가 들어 있습니다. 틀리면 개발자가 화면에서 연결을 바꾸거나 지울 수 있습니다.
다음 단계로 영향 OS 범위를 코드로도 확인하겠습니다.

## 14쪽. 예상 질문 3: 없는 기능을 버그로 보는 문제는 어떻게 줄이나

지금은 분류 지시에 앱의 정상 동작 9가지를 적어 두었습니다. 목록에 있는 동작을 묻는 것만 문의로 보고, 목록 밖은 고장 가능성이 있으면 버그로 봅니다.
일부러 버그 쪽으로 기울였습니다. 250건에서 버그를 놓친 건수는 0, 0, 1건, 버그가 아닌 것을 버그로 본 건수는 7, 5, 5건입니다.
줄이려면 앱에 있는 기능 목록을 제품 담당자가 확정해서 넣어야 합니다. 규칙을 넓게 썼다가 진짜 버그 3건을 문의로 보낸 적이 있어서(V2-Run-09), "목록에 있는 동작"으로 좁혀 0건으로 되돌렸습니다(V2-Run-10). 바꿀 때마다 새 사례로 다시 재야 합니다.

## 15쪽. RunBuddy 앱 (20초)

러닝 거리와 페이스를 기록하고 AI가 코스를 추천해 지도에 그려 주는 안드로이드 앱입니다. 2025년 9~12월 전공 수업에서 세 명이 만들었고, 저는 AI 채팅과 OpenAI 연동, 러닝 중 지도 표시를 맡았습니다.

## 16~17쪽. 설계 표와 원칙

글을 이해하고 판단하는 일은 LLM이, 규칙이 정해진 일과 확인은 코드가 맡습니다. 규칙으로 답이 정해지는 일은 AI에게 맡기지 않는다는 원칙입니다.

## 18쪽. 우선순위와 완성도

우선순위는 얼마나 급한지, 완성도는 정보가 얼마나 충분한지입니다. "자꾸 튕겨요"는 앱이 꺼지니 P1이지만, 버전과 재현 방법이 없어 완성도는 1점입니다.

## 19쪽. 고친 것 7가지 전체

본론에서는 3번과 5번만 말했습니다. 1번 채점 기준표·예시·필요한 정보만 전달하기로 우선순위가 0.672에서 0.864가 됐습니다(전 값은 1회).

## 20쪽. 기법 비교 [줄여도 됨]

기법을 하나씩 꺼서 250건을 세 번씩 쟀습니다. 채점 기준표를 끄면 우선순위가 0.864에서 0.712로, 완성도 오차가 0.120에서 0.403으로 나빠져 효과가 가장 컸습니다. 4단계로 나누는 것은 모든 면에서 좋지는 않았고, 완성도는 한 번에 시킨 쪽이 더 좋았습니다. 효과가 확인되지 않은 것(context 선별, effort)도 그대로 적었습니다.

## 21쪽. 공통 필수 조건

강의의 공통 필수 조건을 서비스 어디에 넣었는지 정리한 표입니다.

## 22~30쪽. 실제 화면

신고자 화면(22~27쪽): 신고 전에 알려진 문제와 점검 방법을 먼저 보여 주고, 러닝 기록·기기 정보·사진·로그를 선택해서 붙일 수 있고, 접수하면 개인 링크에서 AI의 추가 질문과 개발자 답변을 봅니다.
개발자 화면(28~30쪽): 급한 순서로 정리된 제보, 판단 근거와 부족한 정보, 챗봇입니다. 모두 임시 데이터로 실제 앱을 실행해 찍었습니다.

## 막힐 때 쓰는 한 문장

- **도구가 뭐냐고 하면:** AI가 외워서 답하지 않고, 필요할 때 부르는 검색 기능입니다.
- **MAE가 뭐냐고 하면:** 정답과 평균 몇 점 차이 나는지입니다. 작을수록 좋습니다.
- **헤드리스가 뭐냐고 하면:** Claude Code를 화면 없이 프로그램에서 부르는 방식입니다. API 키 대신 로그인 계정을 씁니다.
- **왜 느리냐고 하면:** 호출할 때마다 Claude Code를 새로 켜서 한 건에 12~30초 걸립니다. API 방식은 약 9초였습니다.
- **모르는 질문이면:** 그 부분은 확인하지 않았습니다. 확인하려면 ○○를 재 보면 됩니다. (추측으로 답하지 않기)
