## Run별 해석

- **Run-01 (기준선)**: 분류·링크는 지시문만으로도 이미 높다(분류 1.00). 약점은 우선순위 P1 과소평가(P1 16건 중 15건을 P2로)와 완성도 2→1 과소평가(19건). 기준이 없으니 보수적으로 매긴다.
- **Run-02 (+Few-shot)**: 우선순위 0.76→0.79, MAE 0.41→0.34로 점수 쪽이 조금 좋아졌고 응답시간이 9.3→8.0s로 줄었다(출력 형식이 짧아짐). 대신 hard 2건(E-021, E-052)이 bug로 오분류되기 시작했다. 예시가 "안 보여요/안 나와요" 표현을 버그 쪽으로 끌어당긴 것으로 보인다.
- **Run-03 (+Rubric)**: 완성도 MAE 0.34→0.18로 절반, 우선순위 exact 0.79→0.82. 채점 기준표가 점수 단계에 가장 효과가 큰 변수였다. 비용은 거의 같다(Rubric이 캐시 블록에 들어가 cache_read만 늘어남).
- **Run-04 (+Context 선별)**: 링크·스코어 단계에 원문 대신 추출 결과만 주자 MAE 0.18→0.11, 우선순위 0.82→0.84. 입력 토큰이 줄어 비용도 소폭 감소. 품질 손실 없이 비용이 줄어서 기본 설정으로 유지한다.
- **Run-05 (Sonnet)**: 우선순위 0.93, MAE 0.04로 점수 단계는 확실히 낫다. 하지만 비용 17.7배($0.089→$1.568), 응답시간은 Run-04 대비 +32%(8.26→10.93s). 추출 정확도는 Haiku 개선판(Run-06/07, 0.972)보다 낮고(0.962), 문의·개선 요청의 feature_area를 null로 두는 문제는 Sonnet에서도 똑같았다. 모델이 아니라 프롬프트 정의 문제라는 증거다.
- **Run-06 (개선1)**: feature_area 누락 13건→0건, 추출 정확도 0.950→0.972, 누락률 0.068→0.005. 환각률이 0.018→0.025로 조금 늘었는데, 정답이 null인 2건(E-006 "안드로이드 7에서도 돌아가나요?", E-096)을 `other`로 채운 탓이다. 부작용: 완성도 MAE 0.107→0.143, 우선순위 ±1 0.98→0.97로 나빠졌다(스코어 프롬프트는 그대로라 추출 변경의 간접 영향이거나 Run 간 변동일 수 있음). 분류·링크는 동일. 추출 이득(누락 13건 해소)이 더 커서 **유지.** MAE는 Run-07에서 0.109로 돌아왔다.
- **Run-07 (개선2)**: 우선순위 exact 0.84→0.88, ±1 0.97→0.99, P1 재현율 10/16→15/16. 과대평가 부작용은 1건(E-065 P2→P1). 완성도 MAE도 0.143→0.109(Run-04의 0.107 수준으로 회복). 추출 지표는 그대로. **유지 → 최종 설정.**

## 최종 설정

Haiku 5.5 + few_shot + rubric + context_select + 개선1·2 (= Run-07). 근거는 `docs/HISTORY.md`와 `docs/analysis/error_analysis.md` 참고.
- 품질: 분류 정확도는 같고(0.98), 추출 정확도는 Haiku가 높다(0.972 vs 0.962). Sonnet이 labels 정확도 0.03(0.98 vs 0.95), 링크 0.01(0.97 vs 0.96), 우선순위 exact 0.05(0.93 vs 0.88), 완성도 MAE(0.036 vs 0.109)에서 앞선다.
