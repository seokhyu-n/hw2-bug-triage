읽는 법
- 끄기 실험과 Sonnet은 **1회씩**이다. 튜닝 전 설정의 3회 범위를 크게 벗어난 값만 효과로 본다. CoT는 점수 단계에만 쓰이는데 V3-Run-06의 분류가 0.936으로 나왔다(튜닝 전 3회는 0.940~0.956). 즉 **분류는 효과가 없는 변화에서도 1%p 넘게 흔들린다**.
- **Rubric**: 우선순위와 완성도에서 가장 크다. **CoT**와 **few-shot**: 완성도에서 보인다. few-shot의 우선순위, context 선택 전체, effort medium은 차이가 확인되지 않았다.
- **체이닝**: 4단계가 모든 지표에서 낫지는 않다. 한 번 호출은 완성도 MAE가 더 좋고(0.037), 추출 환각률과 비용은 나쁘다. 또 한 번 호출은 API의 스키마 제한(union 파라미터 19개로 400 오류, 250건 전부 실패) 때문에 null 문자열을 ""로 받아 되돌리는 다른 스키마를 써서 순수한 체이닝 비교가 아니다. 이 설정은 세 번 돌렸다: 첫 실행은 전부 실패, 두 번째는 모델이 쓴 글자 "null"을 값으로 채점, 세 번째가 위 표다.
- **Sonnet**: 대부분 지표가 가장 높지만 비용이 약 18배다. 1건(E-189)은 출력이 잘려 실패했고 오답으로 셌다.
- 응답시간은 여러 평가를 동시에 돌려서 비교에 쓰지 않는다.

## 4. 새 사례 검증 (holdout 100건)

튜닝 프롬프트·v3·결과를 주지 않은 에이전트가 튜닝 전 규칙만 보고 썼다. 실행 전에 사례와 프롬프트의 해시를 고정했고, 이 결과를 보고 프롬프트를 더 고치지 않았다. 튜닝 전 = 커밋 e0e6b82의 프롬프트(`--prompts-dir`), 코드는 같다. 각 3회.

| 지표 | 튜닝 전 (범위) | 튜닝 후 (범위) | 판단 |
|---|---|---|---|
| 분류 | 0.950 (세 번 같음) | 0.993 (0.99~1.00) | 좋아짐 |
| labels | 0.973 (0.96~0.98) | 0.980 (0.97~0.99) | 차이 확인 안 됨 |
| 우선순위 exact | 0.947 (0.94~0.95) | 0.977 (0.95~0.99) | 확실하지 않음(범위가 0.95에서 맞닿음) |
| 완성도 MAE | 0.147 (0.111~0.182) | 0.122 (0.091~0.145) | 차이 확인 안 됨 |
| 링크 | 0.993 (0.99~1.00) | 1.000 (세 번 같음) | 1건 안팎 |
| 추출 | 0.974 | 0.975 | 차이 없음 |

- 분류에서 고쳐진 4건(E-393, E-397~E-399)은 모두 "기능이 있는지 묻고 추가도 요청"하는 한 유형이다. 규칙 하나의 효과다.
- v3의 labels 상승(0.867 → 0.936~0.944)은 여기서 재현되지 않았다. 튜닝 전에도 0.973이라 더 오를 여지가 적었던 탓일 수 있어 효과가 없다고도 할 수 없다.
- **부작용**: E-342("왜 0'00\"인가요?")에 문의 라벨을 잘못 붙임(3/3, 전에는 0/3). E-333 labels 3/3 → 1/3.
- **정답을 바꾼 영향**: 우선순위는 검토 전 정답으로 0.957 → 0.973이었다. 바뀐 holdout 정답은 E-323(P3 → P2) 하나이고, 튜닝 전 모델은 P3, 튜닝 후 모델은 주로 P2로 답하던 사례라 **튜닝 후에 유리하게** 바뀌었다. 결과를 본 뒤의 검토였고 질문에 "E-204와 같게"라고 적혀 있었다. 그래서 이 차이를 튜닝 효과로 보지 않는다.
- 버그를 놓친 건수 0·1·1 → 0·0·1, 버그가 아닌 것을 버그로 본 건수는 전후 모두 0.
- 한계: holdout이 v3보다 쉽다. 새 제품 정책 3개에 해당하는 사례와 아이폰 사례가 없다. E-332는 v3 E-201과 상황이 비슷하다. 정답은 튜닝 전 규칙으로 매겼다. 작성 에이전트는 프로젝트 안내 문서로 이전 실패 사례 번호 4개(E-053, E-090, E-113, E-116)는 알고 있었다.

**채택**: holdout에서 나빠진 지표가 없고 분류가 좋아져 최종 문구를 서비스 설정(V3-Run-12)으로 쓴다.

- **2번의 1회 해석을 이 표로 고친다.** rubric은 우선순위·완성도에서 가장 크다. CoT는 완성도에서 확실하고 우선순위는 범위가 맞닿는다. few-shot은 완성도에 도움이 되지만 labels는 끈 쪽이 높다(0.888~0.900 대 0.864~0.872). context 선택과 effort medium은 차이가 확인되지 않는다(effort 2·3회차는 1건씩 오류를 오답으로 셌다).
- 한 번 호출(체이닝 끔)은 완성도·labels가 더 좋고 비용이 약 30% 많다. 추출 환각률은 범위가 겹쳐 **더 나쁘다고 할 수 없다**. 다른 스키마를 쓰는 비교라 순수한 체이닝 효과는 아니다.
- 최종 문구(V3-Run-12) 3회의 완성도 MAE는 튜닝 전과 범위가 겹친다. 3번의 "튜닝 전보다 나쁘다"는 1회만 본 말이라 **취소한다**.
- **챗봇 새 사례 100건**(`eval/chat_holdout.py`, 기존 문제를 보지 않은 에이전트 작성, API, 3회씩): 새 규칙 3개를 뺀 프롬프트 98·96·96 → 최종 100·100·100. 차이는 모두 "대상이 불분명한 요청" 12건이다. 따옴표로 인용한 글 8건과 따옴표 없는 글 10건은 튜닝 전에도 통과해 구멍이 드러나지 않았다. 되물었는지는 채점하지 않는다.
- **어려운 추가 기능 셋 v3**(각 100건, V3-Run-12 문구, API 1회): 캡처 보이는 값 96/98·지어낸 값 4/202, 답장 119/122·9/178, 아이폰 우선순위 94/99와 나머지 모두 정답(1건은 출력이 잘려 제외). 이번 설정(V3-Run-15)으로는 **다시 재지 않았다**. 정답은 AI가 썼고 판단이 갈리는 22건은 JSONL의 `review` 칸에 있다.
- 답장 셋에서 찾은 오류: 답장 속 지시로 기종이 바뀜(Q3-093), 남의 폰 값(Q3-052·064), 되돌린 버전을 놓침(Q3-015), 확실하지 않은 값(Q3-039·042·044·047·048), 철자(Q3-067). 당시 "지시문 무시 8/8"은 우선순위만 봐서 Q3-093을 놓쳤고, 지금은 값이 바뀌었는지도 본다.
